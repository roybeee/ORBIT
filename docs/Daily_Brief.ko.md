# 원페이지 실행 제안

`내일 제안 → 원페이지 제안 만들기`와 `회고 저장하고 내일 제안 보기`는 사용자의 연결된 Hermes Agent에서 같은 비동기 분석을 실행한다. 모델 API를 별도로 연결하지 않는다. 대화의 `proposal.generate` / `review.saveGenerate` 승인도 같은 실행 경로로 이어진다.

결과는 판단 요약, 오늘까지의 변화, 목표에 연결한 최대 3개 우선순위(이유·실행 단계·결과물), 뒤로 미룰 일, 장애물 대응, 하루 성공 기준과 확인할 질문을 담는다. `Proposal.brief`에 분석 시점·근거·범위를 함께 저장한다. 기존 기록 형식을 유지하므로 새 DB 마이그레이션은 필요 없다.

## 근거와 범위

- 모든 현재 프로젝트·업무와 완료 결과, 오늘까지 저장한 회고, 기록 목록/요약을 포함한다. 이전 60개 기록/100개 업무 제한을 적용하지 않는다.
- 회의록 본문은 저장된 원문 버전을 읽는다. 초기 본문 전달 예산은 전체 100,000자이며 최근 기록부터 포함한다. 중요한 나머지 원문은 Hermes의 `read_note`로 추가 조회한다. 원문 전체 포함 개수를 표시한다.
- 완료된 대화는 최근 50건, 각 사용자·응답 부분은 최대 4,000자씩 참고한다. 현재 업무 상태는 과거의 상태 변경 이력을 재구성한 것이 아니다.
- 연결된 Google 기본 캘린더를 갱신한다. 동기화 실패 시 저장된 일정을 사용했다는 안내를 남긴다. 외부 전체 캘린더 이력을 분석했다고 표시하지 않는다.
- Plaud가 연결되면 실제 읽기 도구 스키마를 가져오고 적어도 조회를 시도하도록 요구한다. 조회 결과만 근거로 인정하며 전체 보관함을 읽었다고 주장하지 않는다. 성공한 조회의 인수와 발췌를 근거에 남긴다.
- 기록이 없거나 원문/연결 조회가 부분적이면 질문과 분석 범위에 표시한다. UTF-8 기준 실행 저장 한도를 넘으면 명시적으로 실패하고 기존 계획을 유지한다.

## 실행과 승인

Hermes는 우선순위를 정하고 구체적 방안을 제시한다. 기존 시간 배치기는 고정 일정, 컨디션, 업무 요일, 보류, 선행 작업과 집중 개수 제한을 검사한다. 기존 업무의 소요시간은 저장된 실제 추정값을 사용한다. 회의록에서 새로 도출한 후속 업무는 제안 내부의 초안으로만 남으며 승인할 때 업무와 Orbit 집중 시간을 함께 만든다. Google 등록이나 외부 연락을 자동 실행하지 않는다.

분석 결과 저장과 실행 완료 상태는 하나의 트랜잭션으로 처리한다. 분석 도중 기록 변경 또는 취소가 먼저 반영되면 새 제안은 게시되지 않는다. 응답 유실 뒤 재시도는 동일한 실행 번호와 저장된 결과를 확인한다. 기존 승인·보류 항목은 재생성에도 유지한다.
