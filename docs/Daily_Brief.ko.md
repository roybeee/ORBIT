# 원페이지 실행 제안

`내일 제안 → 원페이지 제안 만들기`와 `회고 저장하고 내일 제안 보기`는 사용자의 연결된 Hermes Agent에서 같은 비동기 분석을 실행한다. 모델 API를 별도로 연결하지 않는다. 대화의 `proposal.generate` / `review.saveGenerate` 승인도 같은 실행 경로로 이어진다.

결과는 판단 요약, 오늘까지의 변화, 목표에 연결한 최대 3개 우선순위(이유·실행 단계·결과물), 뒤로 미룰 일, 장애물 대응, 하루 성공 기준과 확인할 질문을 담는다. `Proposal.brief`에 분석 시점·근거·범위를 함께 저장한다. 중간 분석은 소유자·실행별 `orbit_brief_parts`에 분리 저장하며 마이그레이션 0023이 필요하다.

## 근거와 범위

- 모든 현재 프로젝트·업무와 완료 결과, 오늘까지 저장한 회고, 기록 목록/요약을 포함한다. 이전 60개 기록/100개 업무 제한을 적용하지 않는다.
- 회의록 본문은 저장된 불변 원문 버전을 끝까지 수집한다. 크기 때문에 본문·요약의 뒤를 자르지 않는다. 읽지 못한 원문은 범위 안내에 남긴다.
- 완료된 Orbit 대화는 오늘까지 전부 수집하며 사용자 발언과 이전 AI 답변을 구별한다. 현재 업무 상태는 과거 상태의 복원이 아니다.
- 오래된 완료 업무도 개수로 대체하지 않고 실제 기록과 결과를 포함한다.
- 연결된 Google 기본 캘린더를 갱신한다. 동기화 실패 시 저장된 일정을 사용했다는 안내를 남긴다. 외부 전체 캘린더 이력을 분석했다고 표시하지 않는다.
- Plaud가 연결되면 실제 읽기 도구 스키마를 가져오고 적어도 조회를 시도하도록 요구한다. 조회 결과만 근거로 인정하며 전체 보관함을 읽었다고 주장하지 않는다. 성공한 조회의 인수와 발췌를 근거에 남긴다.
- 기록이 없거나 외부 연결 조회가 부분적이면 질문과 분석 범위에 표시한다. 로컬 분석 대상의 총 글자 수를 이유로 중단하거나 기록 정리를 요구하지 않는다.

## 전체 자료 분할 분석과 이어가기

한 번에 보낼 자료가 크면 최대 16,000자 단위로 자동 분할한다. 큰 개별 기록은 경로·오프셋·근거 ID를 붙여 끝까지 나눈다. 전체 묶음 개수의 상한은 없다. 각 묶음은 독립적인 Hermes 실행으로 분석하며 완료 결과를 DB에 저장한다. 중간 결과도 크면 다시 여러 묶음으로 통합하는 계층형 분석을 반복한다. 최종 판단은 압축된 분석 결과를 활용하므로 원문과 같다고 주장하지 않으며, 중요한 원문은 추가 조회한다.

화면에는 원문 검토/결과 통합 단계, 현재 묶음과 처리 개수를 표시한다. 앱의 기존 실행 폴러 또는 활성화된 서버 런타임이 다음 묶음을 이어간다. 진행 중인 묶음의 일시 오류나 gateway 실행 기록 유실은 그 묶음만 최대 두 번 재시도하며 앞서 끝난 결과는 유지한다. 각 묶음에는 개별 실행 시간 제한이 적용되지만 전체 분석을 30분으로 제한하지 않는다. 인증 실패·실행 중지·장시간 응답 없는 단일 실행은 기존 오류 처리로 종료한다.

자료가 적으면 직접 분석하며, 모델 실패 시 전송 예산을 조정한다. 데이터 자체를 줄이지 않고 필요하면 분할 경로를 사용한다. 외부 Plaud/Google 조회는 실제 연결 권한과 조회 성공 범위에 한정되며 외부 전체 보관함 자동 수집을 의미하지 않는다. 추가 조회의 단일 응답과 모델 컨텍스트에는 기술적 한도가 있다.

원본 근거는 중간 요약과 별도로 저장한다. 최종 인용은 같은 소유자·실행의 원본 근거로 검증한다. 전체 분석 전에는 결과를 게시하지 않으며 기존 계획을 유지한다. 완료·취소·실패 시 임시 분석 자료를 정리한다.

## 증분 분석과 재사용

카탈로그는 원문 단위(기록별 문서, 프로젝트별 미완료 업무, 월별 완료 업무·일정, 연도별 회고, 일별 대화, 결정·위임·기억 등)와 매번 새로 보내는 frame(설정, 목표와 규칙 ★, 습관·리스크·주간 통계, 운영 신호, 후속 확인, 최근 계획, 가용 시간)으로 나뉜다. 각 원문 묶음과 통합 단계의 입력은 내용 해시로 `orbit_analysis_cache`에 저장한 분석과 대조하며, 내용이 같으면 Hermes를 다시 호출하지 않는다. 재사용하는 분석도 형식과 근거 ID를 다시 검증하고, 실패하면 새로 분석한다. 수정·삭제·추가된 기록은 해당 단위와 그 상위 통합만 다시 계산하고, 최종 합성은 항상 새로 실행되며 이전 게시 이후 바뀐 기록 그룹 목록(changes)을 받는다. 분석 지시문이 바뀌면 버전이 바뀌어 전체를 다시 분석한다. 실행마다 `orbit_brief_runs`에 시작·반영 기준·준비 완료 시각과 재사용 개수를 기록하고, 홈 화면의 계획 준비 상태와 `GET /api/brief/status`에서 최근 7일 기록을 확인할 수 있다. 아침 준비 여부 기준은 소유자 시간대의 07:00이다.

## Goal Laser와 BRAINY 프레임

카탈로그의 `brainy`에 도미노 프로젝트, 목표 계층, 규칙 ★, 습관과 D+ 연속일, 상시 리스크, 이번 주 실행률과 어제 회고 통계가 들어간다. Hermes는 1순위를 도미노 프로젝트에서 고르도록 요청받으며, 각 우선순위에 인지 등급(고위·중위·저위·외부)과 사분면(A/B/C/D)을 붙일 수 있다. 시간 배치기는 연속 집중이 필요한 첫 우선순위(고위 인지, 90분 이상, 도미노 프로젝트 45분 이상)를 오늘의 Goal Laser로 두고 집중 구간에 설정한 연속 시간(기본 180분)을 먼저 확보한다. Laser 앞에 둔 짧은 선결 업무는 그보다 먼저 배치한다. 확보하지 못하면 이유를 그대로 표시하고 부분 배치를 하지 않는다. 기존 업무의 예상 시간은 최근 실적의 실제÷예상 중앙값으로 보정한다.

Hermes가 연결되어 있지 않으면 같은 요청이 Orbit의 규칙 기반 계획(점심·이동 버퍼 → Goal Laser → 반드시 종결 → B → A → C, D는 위임 목록)으로 시간을 배치하고 화면에 그 사실을 알린다. 연결된 Hermes의 실행이 끝내 실패한 경우(프로바이더 사용량 한도 소진·인증 실패·30분 초과 등)에도 같은 규칙 기반 계획이 그 날짜를 대신 채우고, 분석 오류에 그 사실을 덧붙인다. 이미 그 날짜에 계획이 있으면 덮어쓰지 않는다. 사용량 한도가 소진된 실행은 분량을 줄여 다시 보내지 않는다 — 같은 카탈로그를 다시 보내도 한도는 회복되지 않기 때문이다. 저녁 회고의 PAFI 상세(결과·실제 시간·규칙·습관·에너지)는 분석 시작 전에 `orbit_reviews`에 저장된다.

## 실행과 승인

Hermes는 우선순위를 정하고 구체적 방안을 제시한다. 기존 시간 배치기는 고정 일정, 컨디션, 업무 요일, 보류, 선행 작업과 집중 개수 제한을 검사한다. 기존 업무의 소요시간은 저장된 실제 추정값을 사용한다. 회의록에서 새로 도출한 후속 업무는 제안 내부의 초안으로만 남으며 승인할 때 업무와 Orbit 집중 시간을 함께 만든다. Google 등록이나 외부 연락을 자동 실행하지 않는다.

분석 결과 저장과 실행 완료 상태는 하나의 트랜잭션으로 처리한다. 분석 도중 기록 변경 또는 취소가 먼저 반영되면 새 제안은 게시되지 않는다. 응답 유실 뒤 재시도는 동일한 실행 번호와 저장된 결과를 확인한다. 기존 승인·보류 항목은 재생성에도 유지한다.
