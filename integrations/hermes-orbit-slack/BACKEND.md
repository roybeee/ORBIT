## Implemented

`app/api/integrations/slack/directives/route.ts` delegates to the real D1-backed service in `lib/orbit/slack/directives.ts`. It uses canonical `readWorkspace`, `writeCommand`, `readNote`, note revisions, workspace chunks and mutation receipts; no parallel fake note store.

- Only `change.kind=note` is supported, creating a canonical `kind=knowledge` note. Text/order are preserved. Canonical note `updated` holds the supplied date; API readback exposes it as `date` for v2 compatibility. No filesystem KB adapter. Existing `/home/hermes/mealzip-knowledge/projects/old-ferry-donut.md` is neither reread nor rewritten by this service.
- A single integration credential is bound server-side to owner + Slack workspace + requester, with `directives:write` scope, expiry and revocation. Raw credentials are never stored. Neither posted owner IDs nor browser/platform auth headers grant integration authority.
- Trusted transport attestation boundary: the scoped integration caller is responsible for authenticated Slack event provenance. This endpoint does NOT independently prove Slack event authenticity or user approval. Never expose the credential to model inputs or untrusted callers. Gateway envelope/alias defects remain release blockers.
- `GET ?resolveProjectId=...&workspaceId=...&requesterId=...` authorizes the project in the credential owner's actual workspace. Posted v2 binding must match this server-derived authority.
- `POST` persists the immutable bounded wire payload and receipt. Operation identity is owner/workspace/requester/operationKey; sorted-key payload hash rejects conflicting reuse (409). Credential rotation preserving principal does not lose reconciliation access.
- Successful notes and receipts commit in one D1 atomic batch using a new optional canonical repository transaction extension. Credential authority is rechecked in the committing statement; canonical workspace revision prevents project authorization from racing a project edit/delete. Any receipt insert failure rolls back workspace/chunks/note revision/mutation. Duplicate races reconcile the winner.
- `GET ?id=...` or `?operationKey=...` reads canonical note data, not an echoed target in receipt JSON. Edited/deleted targets report `target_changed`/`target_missing`, never completed. A lost commit acknowledgement is reconciled from durable state; a 404 is not permission to blindly retry a provider write.
- Missing/name-only project stores `needs_confirmation` with at most eight owner-scoped canonical project IDs and no note. Explicit unauthorized IDs get 403. Failed provider stores `provider_failed` and no target. No provider network request or calendar outbox entry is made.
